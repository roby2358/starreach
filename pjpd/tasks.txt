Event architecture: push what happens in a game, not only what it now looks like, to viewers. Today a viewer's socket carries `{type: "view", view: GameView}` frames after each accepted command, while events are plain strings in the MCP Result that only the caller sees (D-17). Design structured events (for example `{type, from, to, damage}`) in the Rust core, with the strings still derived for the LLM, and send them as a new frame type on the same socket, so the page can animate beams, torpedoes, hits, warps and hails. One `apply` runs the ship's action and then the enemy turn, and today the viewer sees only the final board. The core must emit a command's events in the order they happened (the ship's action first, then each enemy's move and shot), and the page plays them back in that order, so a viewer sees the ship act and then the enemies respond, and a hit or kill flashes on the right cell (the Holotank page currently flares the whole plane because a frame can't say which enemy died). This replaces any idea of capturing board snapshots between the two halves. Decide: event visibility per player for multiplayer (see RATIONALE Q-19); an ordering sequence number; replay or catch-up when a viewer reconnects; and how it maps onto one Durable Object per game, which would be the natural sequencer. Colour such as messages from Star Central could travel this way. Update ONTOLOGY (Event, Viewer socket), RATIONALE D-17, and CRITERIA. Ask the user before committing.
