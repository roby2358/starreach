The telemetry report drops the command that ended a game when that command took no game time.

Where: `tools/telemetry_report/figures.ts`, `gamePlays()`. For an ended game it takes the "played events" as the events up to the last one with `ticks > 0`, on the assumption that the command that ends a game always takes time.

Why that is wrong: in the core's Warp rule (`core/src/actions.rs`, `warp`), the enemies in the current sector get a turn before the ship leaves. If that turn brings the hull to 0, the warp returns as an accepted command without leaving: no energy spent, no time passed, report `{sector_xy: <the sector the ship is in>, energy_cost: 0, time: "0.00.0"}`, and the Game end rule then marks the game lost. Its telemetry event is `accepted: true`, `tool: "galaxy_warp"`, `ticks: 0`, detail `{distance: 0, energy_cost: 0, shield_recharge: 0}`. Likely fix (confirm with the designer): take the ending event as the game's last accepted event whose tool is an action (not `state` or `galaxy_map`), since after the end every action is refused with "The game is over" and only queries are accepted; and leave an accepted `galaxy_warp` with `ticks` 0 out of the Warp section and of Looking before leaping, or show it apart. Add a case to the report's fixed test records (`app/test/helpers/report_play.ts`, tests under `app/test/R-52/`): a game lost to the parting turn before a warp.

Move the telemetry player-hash salt out of the code and into a Worker secret.

Goal: a leaked telemetry database cannot be matched to players by someone who only has the public repo. Today the salt is a named constant in a public repository, so anyone holding telemetry rows can hash a known player id and find that player's games. Accepted for now because the database is private and the data is game moves; this is the fancier version for when the game has more players.

Assumes telemetry is being recorded with a player hash salted by a constant in the code. If it is not yet, this cannot be started.

Design:
- On Cloudflare the salt comes from a Worker secret (set with `wrangler secret put`), read where the hash is made. A missing secret fails fast at startup or first use; no fallback to a built-in value.
- Locally the salt comes from a development variable with a fixed, obviously non-secret value, so local play and tests need no setup.
- The constant is removed from the code. Changing the salt starts the count of returning players afresh; that is acceptable, since players need only be followed over a few weeks. Say so in the architecture log.
- First check what the hashed player id is: if it is a public identifier such as a Bluesky DID, this change matters; if it is an id internal to the sign-in service, note that in RATIONALE, since the exposure is then smaller.
- Once done, the home page's privacy line may be strengthened to match.
- Docs: the RATIONALE decision on the hash, ONTOLOGY's numbers or configuration, the recipes skill (the one command to set the secret), ARCHITECTURE_LOG.

Done when:
- No salt value appears in the repository other than the local development one.
- A test shows the hash differs under a different salt and that a missing secret is refused.
- `just cc-test-all` and `just cf-deploy --dry-run` pass.

Setting the production secret is a production change: write the recipe and the steps, but leave running it and the deploy to the designer.
