Client ID Metadata Documents (CIMD) in yuwakisacloud's auth/, with tokens bound to the resource URL, so players add Starreach's MCP connector with just the URL: no client ID to type, no OAuth settings, no fixed callback port.

Today auth/ only knows admin-created clients, so every MCP client shares Starreach's pre-registered public client: claude.ai needs "Use your own OAuth client" plus the client ID, and Claude Code needs `--client-id` and `--callback-port 8574`. With CIMD (the MCP spec's preferred registration after pre-registration), the client_id is an HTTPS URL to the client's own metadata document, e.g. claude.ai's `https://claude.ai/oauth/mcp-oauth-client-metadata` and Claude Code's `https://claude.ai/oauth/claude-code-client-metadata`. claude.ai picks CIMD by itself when the authorization server metadata advertises `client_id_metadata_document_supported: true` and `none` in `token_endpoint_auth_methods_supported`; Claude Code discovers it automatically too.

Decided [D]: the token's audience is the resource URL. auth/ honours the RFC 8707 `resource` parameter MCP clients already send (`https://starreach.yuwakisa.com/mcp`) and writes that URL into `aud`; Starreach pins its own resource URL instead of a client id. This is the MCP spec's default shape, which suits Starreach as a reference implementation, and it separates the two roles the client id plays today: the client id says which app is asking (the grant: redirect URIs, binding the code, PKCE), and the resource URL says which server the token is for. Declined: auth/ translating the resource URL back to Starreach's existing id for `aud` (Starreach unchanged, but the client id keeps doing double duty).

Part 1, resource binding in auth/ (needed before CIMD, and safe to ship alone):
- A registry of resource servers in auth/ (admin-created): the exact resource URL, and the scopes it accepts. auth/ refuses a `resource` that isn't registered, so it never stamps a token for an arbitrary URL.
- /authorize accepts `resource`, validates it, and binds it to the code; /token requires the same `resource` (or none) and sets `aud` to it. Without `resource`, `aud` stays the client_id as today, so existing consumers that pin a client id are unaffected.
- Decide whether a pre-registered client is limited to particular resources (Starreach's own client should only get tokens for Starreach).
- Advertise it (`resource_indicators_supported` or equivalent) if the spec calls for it.
- Rollout: Starreach must accept the new audience before or as auth/ starts issuing it. Either accept both audiences for one deploy, or deploy the two together; tokens last 4 hours.

Part 2, CIMD in auth/:
- Accept a URL-shaped client_id at /authorize and /token: fetch the document (HTTPS only, size and time limits, cached), validate it (its client_id equals the URL, public client, redirect_uris), and match redirect_uri against it. Loopback redirects (`http://localhost/callback`, `http://127.0.0.1/callback`) match on any port (RFC 8252); consider applying that rule to pre-registered clients too, which alone removes `--callback-port`.
- Require `resource` for CIMD clients: their client id says nothing about the target server, so a token without a resource audience must not be issued.
- Decided [D]: open registration. auth/ accepts any HTTPS client metadata document; no allowlist of known clients. A phished player loses a Starreach session, which is only a game, and a consent screen wouldn't stop an inattentive player anyway. What limits the damage instead: the token is bound to the resource it was requested for, carries only that resource's scopes, and expires in 4 hours.
- Because auth/ also serves other consumers, open registration is per resource: each registered resource server says whether metadata-document clients may request tokens for it (Starreach: yes; anything with an `admin` scope: no). A metadata-document client can never get a token without a resource, or for a resource that hasn't opted in.
- Fetch documents safely: HTTPS only, no redirects, size and time limits, no private or internal addresses, cached.
- Show the client's name and the domain of its client id on the sign-in page.
- Advertise `client_id_metadata_document_supported: true` in discovery (both paths).
- Keep pre-registered clients working alongside.

Then in Starreach: pin the audience to the resource URL (one config value; the vendored auth-client's `expected_audience` already does the check), update the R-35 tests' minted tokens, simplify the home page's and README's connection steps to "add the connector URL, sign in with Bluesky", and update the docs (the MCP sign-in decision, R-35, the log).

Ask the user before committing, deploying, or touching yuwakisacloud's production.
