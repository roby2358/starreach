# Starreach — Criteria

How we know Starreach is correct, readable, and good. Rule names refer to ONTOLOGY.md.
Constants are referred to by name; their values are in ONTOLOGY's Numbers table.

**Instrument** is the row's status, in one of exactly four forms: `automated` (tests in
`test/R-n/` run with the normal test command), `manual — <what a human checks>`,
`not yet covered`, or `retired` (a tombstone; the ID is never reused).

**Tests.** Each `automated` R-row owns `test/R-n/` inside the package that owns the code:
`core/tests/R-n/` for rules in the Rust core, `app/test/R-n/` for the app layer, and
`adapters/<platform>/test/R-n/` for an adapter. Each test asserts one rule. Tests seed
the RNG, or build an `ActiveSector` by hand, and never depend on chance. A coverage test in
the core scans every package and fails when an `automated` row has no `test/R-n/`, a
`test/R-n/` has no `automated` row, or an Instrument cell isn't one of the four forms.

## R — Rules (automated)

| ID | Given | Expect | Instrument |
|---|---|---|---|
| R-1 | A newly generated galaxy | The `GALAXY_CENTER` record is `(visible, 0, 1, START_SECTOR_STARS)`. Every other record is hidden, enemies in `0..ENEMY_MAX_PER_SECTOR`, starbases in `{0,1}` (placement is R-34), stars in `STARS_PER_SECTOR`. Over many seeds, mean enemies rise with distance from the center | automated |
| R-2 | Instantiating a sector from its record and the seed | Exactly one `S`. `B` cells match the record's starbase, `E` cells match `enemies_xy` and the record's enemies, `*` cells match its stars. No cell holds two things. The same seed, sector and record give the same board | automated |
| R-3 | `ray(start, dest)` on hand-built maps | `start == dest` → `[start]`. A clear line ends at `dest`. A line through an obstacle ends **at** the first obstacle (included). Leaving the board ends at the first out-of-bounds cell. The start cell is never checked | automated |
| R-4 | `galaxy_warp(x, y)` | The current sector, or energy below the cost → refused, no change. With enemies present, EnemiesTurn runs first, and if the hull reaches 0 the warp doesn't happen and the game is lost. Otherwise: target marked visible; the clock rises by `time = round(WARP_TIME_K × ln(euclid + 1))` starticks, `euclid` in sectors; energy drops by `time × WARP_ENERGY_PER_TICK`; then the shields recharge to `max_shields` by the Shield recharge rule (R-15), paid on top of the warp and reported `Shields recharged by n using m energy`: full shields cost nothing and give no message, too little energy gives a partial recharge (none at 0 energy), the hull is unchanged, and `report.energy_cost` is the warp's alone; the ship meets the arrival ambush with the recharged shields and the enemies there get no other turn; the shortest warp takes more than a long battle does, and over every distance on the map a longer warp takes longer and costs more (D-5); new ActiveSector built; `last_event_startick = startick`; StarbaseHail fires iff the sector has a starbase | automated |
| R-5 | `subwarp(dest)` | Ship moves along `ray` and stops before an obstacle. Steps are capped at `SUBWARP_MAX_STEPS_HOSTILE` with enemies present, else `SUBWARP_MAX_STEPS`. Zero steps, or energy below `steps × SUBWARP_ENERGY_PER_STEP` → refused, no change. Otherwise energy drops by `steps × SUBWARP_ENERGY_PER_STEP`; the clock rises by `steps × SUBWARP_TIME_PER_STEP`; map `S` moves | automated |
| R-6 | `dock()` | Refused with no change when enemies are present, when there is no starbase, or when the starbase isn't within Chebyshev distance 1. On success: hull, shields, energy and torpedoes go to max, and the clock rises by `DOCK_TIME` | automated |
| R-7 | `long_range_scan()` | `energy < LRS_ENERGY` → refused, no change. Otherwise energy drops by `LRS_ENERGY`; the 3×3 block around `sector_xy` becomes visible; `report.scan` shows in-bounds sectors as `"E\|B\|S"` and out-of-bounds ones as `"....."`; the clock rises by `LRS_TIME` and `report.time` is `LRS_TIME` as a duration; with enemies present each acts once after the scan; in a cleared sector no enemy event occurs | automated |
| R-8 | `galaxy_map()` | 10 rows of 10 space-separated entries. A visible record shows `"E|B|S"` and a hidden one `"....."`. Calling it doesn't change state | automated |
| R-9 | `blast(target)` | No enemy first on the ray (or the ray is blocked by a star or starbase) → refused, no change. `euclid(ship, hit enemy) > BLAST_RANGE` → refused. A target cell beyond range is fine when the hit enemy is within it. Energy below `int(BLAST_ENERGY_BASE × √r)` → refused. Otherwise, hit or miss, energy drops by that cost and the clock rises by `int(BLAST_TIME_A + BLAST_TIME_B × √r)`, with `r` measured to the hit enemy. A kill removes the enemy; a miss leaves it and the galaxy record as they were and reports `Blaston beam misses…` first in `events`. `report.destroyed` says which | automated |
| R-10 | `torpedo(target)` | No torpedoes, energy below `TORPEDO_ENERGY`, or no enemy first on the ray → refused, no change. Otherwise the first enemy is removed (any range); torpedoes −1; energy drops by `TORPEDO_ENERGY`; the clock rises by `TORPEDO_TIME` | automated |
| R-11 | An action leaves `startick − last_event_startick = t` | Stardate events run iff `t ≥ EVENT_INTERVAL`, in the order ShieldReplenish then EnemiesTurn, and only those whose `can_occur` is true. `last_event_startick` is set to `startick` only when they run (or on arrival in a sector), so short actions accumulate | automated |
| R-12 | EnemiesTurn with `n` enemies | Every enemy acts exactly once, in `enemies_xy` order, either advancing or firing. Over many seeded turns the advancing share is close to `ENEMY_ADVANCE_FRACTION`, and a lone enemy sometimes advances | automated |
| R-13 | Head-on enemy advance | The enemy moves to `path(enemy, ship)[min(ENEMY_ADVANCE_STEPS, len−1)]` when that cell is empty. Otherwise it stays and reports blocked. It never lands on the ship, a star, the starbase, or another enemy | automated |
| R-14 | Enemy fire at a given damage factor | A blocked ray deals no damage. Otherwise `damage = round(base(d) × factor)`, where `base` is `ENEMY_FIRE_BASE` at 1, `ENEMY_FIRE_NEAR` at `ENEMY_FIRE_NEAR_RANGE`, `ENEMY_FIRE_FAR` at `ENEMY_FIRE_FAR_RANGE` and beyond, the geometric mean of near and far midway between, with the same ratio for each cell. Shields absorb first and the rest goes to hull; neither drops below 0. At any factor in the band, damage strictly decreases with `d` out to `ENEMY_FIRE_FAR_RANGE` | automated |
| R-15 | ShieldReplenish fires; the Shield recharge rule at a limit | Shields rise by `points = min(limit, max_shields − shields, energy × SHIELD_POINTS_PER_ENERGY)` and energy drops by `ceil(points ÷ SHIELD_POINTS_PER_ENERGY)`, so 1 point costs 1 energy and one more than a multiple costs the next whole energy. ShieldReplenish's limit is `SHIELD_REPLENISH`. A recharge of 0 points gives no message. ShieldReplenish doesn't fire at full shields or with energy below 1 | automated |
| R-16 | Warp into a sector with a starbase | One hail message: "all clear" iff `enemies == 0`, otherwise "under attack" | automated |
| R-17 | A startick count; a new game | The stardate shows as `ddd.dddd.dd.d`: whole stardates (`ticks div STARTICKS_PER_STARDATE`) padded to 7 digits, then three decimals from the remainder, truncated and never rounded, so every startick changes it and the last startick of a stardate rolls into the next. A duration shows the same way with the whole part unpadded (`1.04.0`, `0.00.2`). A new game's clock is the given Unix time in starticks plus `STARDATE_EPOCH_OFFSET` stardates, and the app layer takes that time from the adapter's clock. Every action takes a whole number of starticks, at least one, and reports it as `time` in the duration form; the clock is stored as whole numbers | automated |
| R-18 | MCP tools across games | An unknown `game_id` returns `ok: false`, error "Game not found". A command on game A leaves game B unchanged | automated |
| R-19 | Any sequence of commands | ONTOLOGY's invariants hold after every command (one `S`; `enemies_xy` matches `E` cells and the galaxy record; resource bounds including energy ≥ 0; the clock never decreases; visibility never reverts; status leaves `playing` at most once) | automated |
| R-20 | The same seed, the same start time and the same commands | The same final GameState. A different start time changes the clock and nothing else | automated |
| R-21 | A viewer connected to a game | It gets the game's view on connecting and after every accepted command, and no frame for a refused command or another game. An unknown game, or a stored game the core can't read, closes the socket with 4404. `new_game` reports the viewer's link, which holds the `view_id` and never the `game_id`; the socket path takes a `view_id` and refuses a `game_id`. A `view_id` passed as `game_id` to a tool returns Game not found | automated |
| R-22 | A blast that kills, or a torpedo | The galaxy record for `sector_xy` has `enemies == len(enemies_xy)` | automated |
| R-23 | Hull reaches 0; the last enemy in the galaxy is destroyed; or the ship is stranded (energy below the warp cost to the nearest other visible starbase sector) with no starbase in its sector | `status` becomes `lost`, `won`, or `lost` and an end message is in `events`. Every later action is refused with no change; queries still answer | automated |
| R-24 | Warp out of a sector and back | Stars and the starbase are on the same cells. Enemies stand on the first `len(enemies_xy)` of the cells first generated for them | automated |
| R-25 | Every command, accepted or refused | The Result has exactly `ok, error, events, report, state`. `error` is null iff `ok`; `report` is null when refused. A refused action returns the game unchanged. A coordinate outside `0..9` is refused. A stored game without the current Game fields is not a game to the core, and the app layer answers it with the Game-not-found Result, publishing nothing | automated |
| R-26 | The ship is stranded in a sector with a starbase | The game goes on; energy becomes `max(energy, STARBASE_EMERGENCY_ENERGY)` and the transfer message is in `events` | automated |
| R-27 | A viewer sends frames down its socket, including commands | The game doesn't change. A frame over `VIEWER_MAX_FRAME_BYTES` closes that socket with code 1009 | automated |
| R-28 | The view of any game | A hidden sector is null and a visible one matches its record. Ship, status, stardate, sector and board match the game, and its goals are the game's, with each goal's count, amount and met as the state shows them. It has only the GameView fields | automated |
| R-29 | `state` with `n` enemies in the sector | `enemies` has one entry per enemy, in `enemies_xy` order, each `{xy, range, bearing, clear_shot}`. `range` is `euclid(ship, enemy)` to two decimals, the distance R-9 measures. `bearing` is whole degrees clockwise from up: 0 up, 90 right, 180 down, 270 left, 45 up-right. `clear_shot` is true iff the first enemy on `ray(ship, enemy)` is that enemy, whatever the range: false behind a star or another enemy, and equal to whether `torpedo` at that cell would hit it | automated |
| R-30 | Enemy advance chooses an approach | The approach is drawn from the game's rng: left with probability `ENEMY_OBLIQUE_CHANCE / 2`, right with the same, else head-on (over many seeds all three occur at those shares; same seed, same result). An oblique advance takes `ENEMY_ADVANCE_STEPS` steps, each the head-on step turned one octant left or right, or the head-on step itself when the turned one would be farther from the ship. It never ends farther from the ship, never lands on or passes a star, the starbase, another enemy or the ship, and when a step is blocked it stays and reports blocked, with no fallback | automated |
| R-31 | Warp into a sector with enemies | Each enemy, in order, fires once with probability `ENEMY_AMBUSH_CHANCE` (over many seeds the share of shots is near it; same seed, same result), by the enemy fire rule: damage is enemy fire's (R-14, R-33), a blocked shot does no damage. An empty sector draws no fire. If the hull reaches 0 the game is lost | automated |
| R-32 | A blast's kill chance at range `r` | `BLAST_KILL_CHANCE_NEAR` for `r ≤ BLAST_SURE_RANGE`; `BLAST_KILL_CHANCE_FAR` at `BLAST_RANGE`; the geometric mean of the two at the middle of the falloff, the same ratio for each cell of range across it, and strictly falling. Over many seeds the share of kills at one range is near its chance; same seed, same result | automated |
| R-33 | Enemy fire's damage factor | The factor is drawn from the game's rng in `ENEMY_FIRE_VARIANCE_MIN..ENEMY_FIRE_VARIANCE_MAX`. Damage taken stays between the damage at those two factors, varies across seeds, and is the same for the same seed | automated |
| R-34 | A newly generated galaxy's starbases | Besides the `GALAXY_CENTER` one there are `STARBASE_EXTRA_MIN..=STARBASE_EXTRA_MAX` extra ones over many seeds (every count occurs), at most one per sector. Every pair, home base included, is at least `STARBASE_MIN_SPACING` apart (Euclidean). The same seed gives the same placement. When a placement finds no fit within its tries, placement stops with the starbases so far (forced with zero tries), and never goes above the maximum | automated |
| R-35 | Sign-in on `/mcp` (Cloudflare) | Without a bearer token: 401 whose `WWW-Authenticate` names the protected resource metadata URL and `scope="starreach:play"`. The metadata, at the root and the path-inserted well-known URL, has `resource` = `STARREACH_RESOURCE` and `authorization_servers` = [`AUTH_ISSUER`]. A token signed by auth/'s key whose audience is `STARREACH_RESOURCE` or `STARREACH_CLIENT_ID`, with the play scope, signs in its `sub`; one for any other audience (a near-miss URL included) or issuer, or expired, is 401 `invalid_token`; one without the play scope is 403. `whoami` reports the signed-in `sub`, or `signed_in: false` where the adapter has no sign-in | automated |
| R-36 | The counters of a game; the counter table | A new game's counters are all 0 and `state.counters` reports the game's. Each counter rises by the right amount on its event and no other counter moves: a blast that kills raises `blasts_hit` and `enemies_destroyed`, a miss only `blasts_missed`; a torpedo raises `torpedoes_fired` and `enemies_destroyed`; the last enemy of the sector also raises `sectors_cleared`; a warp that arrives raises `sectors_warped`, and one the parting enemy turn stops doesn't; a dock raises `docks`, a scan `scans`; a starbase whose sector becomes visible by scan or warp raises `starbases_discovered` once however often it is seen again, and Star Central's never does; enemy fire raises `shield_damage` by what the shields absorbed and `hull_damage` by what the hull took, and nothing when blocked; a destroyed ship raises `games_lost`, a win `games_won`, a stranding `games_lost` and `times_stranded`, a stranded ship a starbase rescues none of them. Queries, a subwarp and a refused command change no counter. The counter table has one row per Counters field with a label, and each key reads its own field; the positive counters may be goals and the negative ones may not; every `scale` is 1, 10, 100 or 1000; a `goal_ceiling` is 0 or at least the row's `scale`, and 0 where the counter may not be a goal; it is the same over JSON and through the WASM boundary, where its keys are the keys of `state.counters` | automated |
| R-37 | A counter's ladder | The rungs of a scale are scale × 1, 2, 5, 10, 20, 50, 100 and so on. A total going from `before` to `after` crosses every rung above `before` and at or below `after`, in rising order: several at once, one when it lands exactly on a rung, none between two rungs, none when it doesn't move, and a rung it already stands on is not crossed again. A standing is the last rung at or below a total (none below the first) and the first rung above it. The ladder runs past any total a caller holds. Each counter climbs the ladder of its own `scale`; a key that names no counter has none; the same answers over JSON | automated |
| R-38 | Star Central's messages | Every kind has exactly `WORDINGS_PER_KIND` wordings, all different, and kinds have different keys. Every wording carries each placeholder of its kind once and no other, opens with `Star Central`, and filled leaves no placeholder behind. The caller's roll picks the wording: the same roll the same one, each twentieth of [0, 1) its own, and a roll outside that range still one of them. A missing value or an unknown kind gives no message. A counter that may be a goal takes `lifetime_commendation` and one that may not `lifetime_notoriety`; `commendation` fills the counter's label and the amount into a wording of that kind | automated |
| R-39 | A player's lifetime totals | What an accepted command counted is added to the totals of the player who issued it, whoever started the game: only what that command counted, accumulating across the player's games, and never to another player's. With no sign-in they go to the one local player. A refused command, a query, a new game and an unknown game add nothing. A PlayerStore's addition answers with the touched counters' totals before and after, and a player nobody added to has none. The achievements list has a row per counter of the counter table with the total, the last rung reached and the next. The Cloudflare player object, named by the player id, keeps its totals between requests, a key per counter, keeps every one of many additions made at once, and receives a signed-in player's command made through the Worker | automated |
| R-40 | A lifetime total reaches a rung | The command's `events` gain Star Central's message for that rung exactly once, after the game's own events, in the result the MCP tool returns. A command that crosses no rung gains none; a rung is announced once in a lifetime, by the lifetime total and not the game's count. One command crossing several rungs on several counters gains one message per rung, in counter table order and rising, a commendation for a positive counter and notoriety for a negative one. Each message's wording is picked by its own draw from the app layer's random numbers | automated |
| R-41 | A new game's goals | The game has `GOALS_PER_GAME` goals, unmet, on different counters. Each counter may be a goal and has a `goal_ceiling` above 0, and each amount is a rung of that counter's ladder at or below the ceiling; over many seeds no negative counter and no counter with a ceiling of 0 is ever chosen, and every offered counter comes up about equally often with each of its amounts. The same seed gives the same goals whatever the start time. Choosing them leaves the galaxy and the game stream as generation left them. `state.goals` reports each goal's counter, label, count, amount and met, and `new_game`'s report lists the same goals beside the `game_id` and the viewer's link, also through the MCP tool. The goals cross the JSON boundary under their counter keys; a stored game without goals, or with a goal on an unknown counter, is not a game | automated |
| R-42 | The goal check after an accepted action | A goal whose counter reaches its amount becomes met and the command's `events` gain one `objective_met` message naming its label and amount, exactly once: not before the amount is reached and not again after. `state.goals` shows the count rising and the goal met. A met goal stays met. One action that meets several goals gains a message for each, in the game's goal order. The message follows the game's own events, the end of the game included. A query and a refused command check no goal. The wording comes from the goal's own side stream of the seed: the same commands leave the same game whether or not a goal is announced on the way. In the app layer a command that meets a goal and takes a lifetime total to a rung on the same counter gains both messages, the objective first, after the game's own events; the goal follows the game's count whatever the player's lifetime total | automated |
| R-43 | A view frame's achievements | `new_game` stores the player it ran for beside the game: the signed-in player, or the local player where there is no sign-in. The frame a viewer gets on connecting, with no command run, and the frame published after an accepted command both carry the achievements of that player, a row per counter as the achievements list gives them; the one after a command includes what the command counted. When another player issues the command, the counts go to that player's totals and the frame still carries the starting player's achievements. A frame has `type`, `view` and `achievements` only, and never holds the player's id or the `game_id`. On the Node adapter's sockets they are the local player's; on Cloudflare the game's object holds the player under its own key and the frames on its sockets carry the signed-in player's achievements from the player's object | automated |
| R-44 | A coordinate, wherever it is passed, returned or said | It is x first, the column and then the row. The four coordinate tools declare `x` before `y` and describe their target as `(x, y)`; no tool description and no line of the instructions gives a pair y first. A command reads its `x` and `y` by name. Every pair in a Result's `state` and `report`, in a view and in a stored Game is `[x, y]`, and every message that names a cell or a refused coordinate says `(x, y)`. Maps stay rows of columns: the cell at `(x, y)` is `map[y][x]`. A recorded game, one seed through a fixed list of commands, gives its recorded Results and final Game | automated |
| R-45 | A game's telemetry record | `new_game` leaves one game record in the sink: the telemetry game key of its `game_id`, the start time the core was given, the seed, `RULES_VERSION`, the player hash of the player it ran for (the local player's where there is no sign-in), the MCP client, and `end` null; it has those fields and no others. The client is the name and version declared in `initialize` on a connection that carried one, and the request's `User-Agent` over stateless HTTP, each null where the server can't tell it; the Node adapter's server records into its in-memory sink. Commands on a game that goes on leave `end` null. The command that ends a game completes the record once with the outcome, what ended it (`stranded`, `ship_destroyed` or `galaxy_cleared`), the game's counters as its last Result shows them, and each goal's counter, amount and met; later calls leave it as it was | automated |
| R-46 | Tool calls on a game | Every call leaves one event record, accepted or refused, the queries included, with the event fields and no others, numbered from 0 per game in the order of the calls, under the game's telemetry key, with the tool, its arguments without the `game_id`, and the adapter's clock. `accepted` and `refusal` are the Result's `ok` and `error`; `startick` is the game's clock and `ticks` its rise, at least 1 for an accepted action and 0 for a query or a refusal; energy, shields, hull and torpedoes are the Result's; `damage_taken` is what enemy fire took during the call; `sectors_revealed` and `sectors_cleared` count what the call revealed and cleared. `detail` tells, by tool: a subwarp's cells moved and energy cost; a warp's distance in sectors, energy cost and shield recharge; a blast's range, hit or miss and energy cost; a torpedo's range and hit; nothing more for a dock, a scan, a query or a refusal. A call on an unknown game, `new_game` and `whoami` leave no event | automated |
| R-47 | Every telemetry record of a finished game | None holds the `game_id`, the `view_id` or the player id. The telemetry game key is a hash that differs from the `view_id`, is Game not found as a `game_id`, and names nothing in the GameStore. A player's hash is the same in each of that player's games, differs between players, and is not the bare hash of the player id | automated |
| R-48 | A game record's seed and start time, and its accepted events' tools and arguments in `seq` order | Applied to the core alone they give the final stored Game: for a game started with `new_game` and played to its end, and for a game through every tool with refusals among its calls | automated |
| R-49 | A telemetry sink whose every write fails | `new_game` answers and stores its game; every command gets the Result it gets with a working sink, the same game is stored, and the viewers get a frame for every accepted command; a game can end. Each failed write is logged, as is the in-memory sink's refusal to end a game it has no record of | automated |
| R-50 | Games played on the Cloudflare adapter | Their telemetry records are kept in a lasting store | not yet covered |
| R-51 | `GET /telemetry` | On the Node adapter it returns every record the in-memory sink holds, one JSON object per line: each game record as `{"game": …}` in the order the games started, then each event record as `{"event": …}` in the order received, the records as the sink holds them. A game played over `/mcp` comes out as its game record and one event per tool call, refused calls included; with several games every game's records are there. A server that has recorded nothing answers 200 with no lines, and another method gets 404. The Cloudflare Worker answers the path as it answers any unknown path, after a game was played | automated |
