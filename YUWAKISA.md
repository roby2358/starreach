# Deploying Starreach on yuwakisacloud — recommendation

Reviewed read-only on 2026-11-05: `/work/yuwakisacloud` (auth/, jsonsolver/, site/, docs/, CLAUDE.md). Paths below are relative to that repo unless prefixed. Starreach references use its stable IDs (G-n, D-n, Q-n).

## 1. What yuwakisacloud is, as it matters to Starreach

**Platform shape.** A meta-repo of independent Cloudflare Workers monorepos sharing one Cloudflare account, one zone (`yuwakisa.com`) and one auth service; no shared code between monorepos (`CLAUDE.md:7-14`). TypeScript strict, Node 22, "single language across Workers/DOs/Container/shared packages — no FFI boundaries" (`CLAUDE.md:217-218`). Shared `wrangler` 4.90.0 at the root (`package.json:139-141`); each monorepo has its own `justfile`, `wrangler.jsonc` with an `env.production` block pinning routes and a bare Worker `name` (`auth/wrangler.jsonc:90-110`, `jsonsolver/admin/wrangler.jsonc:64-78`), `workers_dev: false` everywhere (`docs/CLOUDFLARE_PRIMER.md:17`). Static pages are an assets-only Worker (`site/wrangler.jsonc:1-18`) or `assets` on a dynamic Worker where the asset layer answers first and unmatched paths fall through to code (`jsonsolver/admin/src/worker.ts:6-12`, `jsonsolver/admin/wrangler.jsonc:10-13`). CI typechecks/tests; CD deploys on push to `main` gated by a `CLOUDFLARE_DEPLOY` repo variable, running the same `just` recipes as the manual runbook (`.github/workflows/deploy-auth.yml:4-11,62-79`). Same-zone Worker-to-Worker calls must use service bindings, not public `fetch()` (edge 522s observed) (`jsonsolver/admin/wrangler.jsonc:28-44`).

**There is no app/game registry or hosting framework.** Apps are just more Workers on more hostnames. The only state abstractions are per-monorepo: D1 for metadata, SQLite-backed Durable Objects for per-entity actors/locks (`jsonsolver/api/wrangler.jsonc:10-19`, `docs/CLOUDFLARE_PRIMER.md:31-35`). No KV. **No MCP server is live anywhere**: jsonsolver's `/mcp/*` is a throw-stub, not routed (`jsonsolver/admin/src/mcp.ts:5-7`, `CLAUDE.md:152`), and "MCP-spec auth integration (RFC 8414 metadata, RFC 7591 registration)" is an explicit jsonsolver non-goal (`jsonsolver/docs/ONTOLOGY.md:36`). No game conventions exist in the repo; the GameEngine/GameState/GameUI split and seeded-RNG rule live only in the user-level skill `~/.claude/skills/yuwakisa_game_factor/SKILL.md` (five-module split, "all randomness flows through a seeded RNG", "never trust the client").

**Auth (`auth/`).** Three Hono Workers over one D1: `auth` (OIDC issuer, `auth.yuwakisa.com`), `bskyoidc` ("Sign in with Bluesky" OIDC provider, `auth-bsky.yuwakisa.com`), `auth-admin` (console) (`auth/docs/ONTOLOGY.md:151-160`). Users are either admin-created password users or Bluesky-federated users JIT-provisioned on first sign-in; `user_id` ULID is the `sub` of every token (`auth/docs/ONTOLOGY.md:43-57`). Flow: OAuth 2.1 Authorization Code + PKCE S256 only, public clients only (`token_endpoint_auth_methods_supported: ["none"]`), OIDC discovery at `/.well-known/openid-configuration` + Ed25519 JWKS (`auth/src/routes/discovery.ts:33-49`). **Access token is bespoke, not a JWT**: `01.<base64url(Ed25519 sig ‖ CBOR{iss,sub,aud,exp,iat,kid,scope})>`, TTL 4 h, **no refresh tokens** (`auth/docs/ONTOLOGY.md:162-167,29,412`). `aud = client_id`: every client is its own resource server (auth/ D-12, `auth/docs/RATIONALE.md:82-84`). Consumers verify offline via the `auth-client` library (`verifyAccessToken`, JWKS cache, pins `iss`/`aud`/time) and may keep their own users table keyed by `sub`, created on first sight (`jsonsolver/auth-client/src/verify.ts:29-92`, `jsonsolver/api/src/auth.ts:19-47`, contract at `auth/docs/ONTOLOGY.md:364-373`). Clients are admin-created rows (`client_id`, exact-string `redirect_uris`, `allowed_scopes`) via the auth-admin console; **dynamic client registration (RFC 7591) is deferred, explicitly "when MCP interop … arrive[s]"** (auth/ D-22, `auth/docs/RATIONALE.md:89-90`). `/authorize` parses the query with a non-strict zod object, so extra params an MCP client sends (`resource`) are dropped, not rejected (`auth/src/routes/authorize.ts:44-54,96-104`); `state` is required. Per-user authorization is the consumer's job: RS scopes are out-of-band strings (`<service>:read`), `admin` is gated on `is_admin` (`auth/docs/ONTOLOGY.md:178-182`). Hard rule from the repo owner: never build OAuth flows or credential storage into a consumer; consumers are token verifiers only (`CLAUDE.md:189-197`).

## 2. Recommended approach

**Starreach becomes a fourth monorepo, `starreach/`, in the meta-repo pattern: one TypeScript Worker (Hono or raw fetch) with `assets` for `public/`, one SQLite Durable Object per game, auth/ as the identity provider, and the Agents SDK/`@modelcontextprotocol` streamable-HTTP handler at `/mcp`.** This is option (C) from the standalone list, placed inside the platform so auth and ops are inherited rather than rebuilt.

What changes in Starreach:

- **Language: port the ~1000-line pure-Python core to TypeScript.** The platform's posture is single-language TS (`CLAUDE.md:217-218`), the only shared libraries are TS (`auth-client`), and `wrangler`/vitest/CRITERIA-coverage tooling is TS-shaped. Python Workers or a Containers-hosted uvicorn would work technically but fit nothing here: Containers are reserved for "doesn't fit a Worker" cases like Z3 (`docs/CLOUDFLARE_PRIMER.md:57-59`) and bring podman/image builds into the deploy (`CLAUDE.md:77-79`). The core is small, already pure, and the port is a chance to settle Q-10 (seeded `Rando` in `GameState`, per the skill) and Q-12 (one `{ok, error?, events, state}` shape). Keep the Python repo as the oracle: port CRITERIA tests first and diff outputs under a fixed seed.
- **State per game: one Durable Object (SQLite) per game, id = game id.** The DO holds the serialized `GameState` plus owner `sub`; every tool call is `env.GAME.get(idFromName(game_id)).act(cmd)`, which also gives serialization and the natural future multiplayer point. Starreach's non-goal "persistence across a server restart" becomes free. No D1 needed for v1; add a small D1 (`games(game_id, owner_sub, created_at, last_active_at)`) only when listing/leaderboards need cross-game queries (jsonsolver's D1-for-metadata, DO-for-actor split, `docs/CLOUDFLARE_PRIMER.md:51-53`).
- **`session_id` ↔ identity.** Keep `session_id` as the tool argument (G-1 says the LLM holds it), but store the creating user's `sub` in the DO and refuse any tool whose caller `sub` ≠ owner (this is "never trust the client" from the skill, and it fixes the open hole where any session id is playable by anyone). Add a `my_games` tool so a reconnecting Claude can recover its session id. `"default"` goes away (Q-8).
- **MCP transport/endpoint:** streamable HTTP at `/mcp`, bearer-only; drop stdio. Every `/mcp` request runs the auth/ consumer contract: `verifyAccessToken` with `expected_audience = STARREACH_CLIENT_ID`, JWKS fetched over an `AUTH_SERVICE` service binding (copy `jsonsolver/api/src/auth.ts` and the `services` block of `jsonsolver/admin/wrangler.jsonc:41-44,90-93`). On 401 return `WWW-Authenticate: Bearer resource_metadata="https://starreach.yuwakisa.com/.well-known/oauth-protected-resource"` and serve that RFC 9728 document pointing at `authorization_servers: ["https://auth.yuwakisa.com"]`, which auth/ already anticipates (`auth/docs/ONTOLOGY.md:373`, D-22). The Python `instructions` prompt and tool set port 1:1.
- **Browser view (G-3, Q-8):** serve `public/` via `assets` (fixes the broken `css/`/`js/` links), and make `GET /state` a *signed-in* route: the page does the same PKCE redirect-to-auth/ dance as jsonsolver/admin (`/auth/login`, `/auth/callback`, access token in an HttpOnly cookie, `jsonsolver/admin/src/auth.ts:53-106`, `middleware.ts:16-62`) and `GET /state?game=<id>` (default: the caller's most recently active game) reads the DO. Later swap polling for a WebSocket from the DO; not needed to ship.
- **Config/ops:** `starreach/wrangler.jsonc` with `env.production` route `starreach.yuwakisa.com/*`, `durable_objects` + `migrations.new_sqlite_classes`, `assets`, `services: AUTH_SERVICE`, vars `AUTH_ISSUER`, `STARREACH_CLIENT_ID`; a `justfile` (`install-dev`, `dev-up` on a free port, `typecheck`, `test`, `deploy`); a `deploy-starreach.yml` cloned from `deploy-auth.yml`; docs/ carried over with IDs intact. One auth/ client row "starreach" (public, PKCE) whose `redirect_uris` list the claude.ai connector callback(s) and the browser callback, `allowed_scopes` `openid profile starreach:play`.

**What is missing in the platform (work in auth/, small, already on its roadmap):**
1. **RFC 8414 alias** `/.well-known/oauth-authorization-server` on the auth Worker (same body as OIDC discovery; named in D-22). Some MCP clients try it before `openid-configuration`.
2. **Dynamic client registration (RFC 7591)**, or at minimum loopback-redirect matching: `redirect_uris` is an exact-string allowlist (`auth/docs/ONTOLOGY.md:79`), so Claude Code / Inspector style `http://localhost:<random port>/callback` cannot be registered. claude.ai and Claude Desktop connectors use fixed `claude.ai` callback URLs and can be given a pre-registered client id, so Starreach can ship without DCR if those are the only clients; I have not verified the current claude.ai connector UI accepts a public client with no secret, so confirm this first.
3. **Token lifetime.** 4 h access tokens and no refresh (D-15) mean a connector re-authorizes at least every 4 h. Acceptable for a game; if it proves annoying, refresh tokens are "additive on the existing shapes" (`auth/docs/RATIONALE.md:221`), an auth/ change, not a Starreach one.

## 3. Versus the standalone Cloudflare options

| Option | Verdict |
|---|---|
| (A) Python in Containers | Keeps code, but Containers are Paid-only, need podman in the deploy, and still leave state in-process (restart loses games) unless you add a DO anyway. Nothing in the platform helps you. |
| (B) Python Workers + DO | Possible, but no Python precedent or tooling in the repo; `auth-client` is TS; you would reimplement the CBOR/Ed25519 verifier. |
| (C) TS + DO + assets | **Recommended**; identical to this doc minus auth. Doing it inside yuwakisacloud buys the identity service, the deploy/CI pattern and the zone for free. |
| (D) Cloudflare Tunnel to a home box | Fine for a demo; no auth, no persistence, a machine to keep up. |
| Rust core → WASM + TS shell | Adds a build toolchain for a 1000-line core; violates the "no FFI boundaries" posture (`CLAUDE.md:218`). Not worth it unless the core grows a lot. |

## 4. Multiplayer readiness (D-18 is a non-goal today)

The shape above is already the multiplayer shape: the DO is the single serialization point for one game, so "two ships in one game" is an owner list instead of one `sub`, a `join_game(game_id)` tool, and per-player visibility filtering in the DO. Identity is solved: every player is an auth/ `sub` (password or Bluesky), tokens are verified offline, and the public client with PKCE works for any number of users with no per-user config. Cross-game data (lobby, leaderboards, accounts' display names from `/userinfo`, `auth/docs/ONTOLOGY.md:249-254`) goes in a Starreach D1, as jsonsolver keeps its `app_users` keyed by `sub` (`jsonsolver/api/src/auth.ts:54-80`). Live spectating is a WebSocket on the DO. Nothing needs to change in auth/ for this.

## 5. Risks and open questions

- **Can claude.ai/Claude Desktop authorize against auth/ without DCR?** Highest-leverage unknown. *Recommend:* before porting anything, register a throwaway client in auth-admin with the claude.ai callback and point a connector at a 20-line test Worker that only serves RFC 9728 metadata and echoes the bearer. If it fails, DCR in auth/ (D-22) becomes step 0.
- **Will the user play from Claude Code or Inspector (random loopback ports)?** *Recommend:* treat as not required for v1; if needed, add RFC 8252 loopback matching to auth/ `/authorize` (small, well-defined).
- **4 h re-auth.** *Recommend:* accept for v1; measure annoyance; refresh tokens later in auth/.
- **Port fidelity.** Rewriting rules risks silent drift (Q-11, Q-13, Q-14 are live tuning questions). *Recommend:* a seed-for-seed diff is not possible (the Python side is unseeded, Q-10), so port CRITERIA rows as vitest tests and compare distributions between the Python balance model (`just cc-model-balance`) and a TS port of `tools/model_balance.py`.
- **Public exposure of a game with an LLM in the loop.** Tool calls cost nothing but DO wall time; a leaked token can only play that user's games. *Recommend:* require `starreach:play` scope and cap games per `sub` in the DO/D1.
- **Repo placement.** Starreach's git history lives in `/work/starreach`. *Recommend:* new `starreach/` monorepo in yuwakisacloud for the TS code and docs (so CI/CD and CLAUDE.md conventions apply); keep this Python repo as the reference until the port's tests are green, then archive.

## 6. Suggested sequence (each step small and shippable)

1. **Auth spike (no Starreach code):** register a `starreach` client in auth-admin; deploy a stub Worker at `starreach.yuwakisa.com` serving `/.well-known/oauth-protected-resource` and a `/mcp` that returns 401/`WWW-Authenticate` or echoes `sub`; connect it from claude.ai. Outcome decides whether auth/ needs RFC 8414 alias and/or DCR first.
2. **Scaffold the monorepo:** `starreach/` with `wrangler.jsonc` (DO, assets, `AUTH_SERVICE`), `justfile`, tsconfig, vitest, `docs/` copied; wire `auth-client` (copy or publish from jsonsolver; it has no runtime deps beyond `cbor-x`).
3. **Port the headless core** (`GameArtifacts`/`GameState`/`GameEngine` per the factor skill): Galaxy, ActiveSector, Ship, events; seeded RNG in state (Q-10); uniform result shape (Q-12). Port CRITERIA tests; compare against Python under hand-picked scenarios.
4. **DO + MCP:** `GameDO` with `act()`, owner check; tools `create_game`, `my_games`, `state`, `subwarp`, `galaxy_warp`, `long_range_scan`, `galaxy_map`, `dock`, `blast`, `torpedo`; `instructions` prompt. Play it end to end from claude.ai.
5. **Browser view:** assets + `/auth/*` glue + `GET /state` for the caller's latest game (closes G-3, Q-8). Fix the asset links.
6. **CI/CD:** `ci.yml` job and `deploy-starreach.yml`; update root `justfile` `dev-up`/`provision` delegation and `CLAUDE.md` repo-shape list.
7. **Later, only if wanted:** WebSocket push from the DO, D1 for listings/leaderboards, `join_game` (revisit D-18), refresh tokens / loopback redirects in auth/.
